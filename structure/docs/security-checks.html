Security headers and external checks

The response headers that scanners such as Mozilla Observatory check, which of them Wicket sends by default, and the Wicket API or hook that sets each one.

This page describes Wicket 10 and later. For Wicket , see the reference guide for Wicket .

Scanners such as Mozilla Observatory grade a site by the security headers in its responses. Wicket sends some of them itself; the others you add in your application, in the container or in a reverse proxy in front of it.

Headers and who sets them

Header Sent by Wicket by default Set with
Content-Security-Policy Yes, a strict policy with nonces, on every WebPage getCspSettings(), see Configure the Content Security Policy
Cross-Origin-Opener-Policy Yes, same-origin, on every response getSecuritySettings().setCrossOriginOpenerPolicyConfiguration(...), see Isolate the page with COOP and COEP
Cross-Origin-Embedder-Policy As Cross-Origin-Embedder-Policy-Report-Only: require-corp, on every response getSecuritySettings().setCrossOriginEmbedderPolicyConfiguration(...)
Vary: sec-fetch-dest, sec-fetch-site, sec-fetch-mode Only with ResourceIsolationRequestCycleListener registered See Protect against cross-site request forgery
Cache-Control: no-cache, no-store, Pragma: no-cache, Expires Yes, on every WebPage Override WebPage#setHeaders(WebResponse)
Strict-Transport-Security No Your own code, the container or the proxy
X-Content-Type-Options: nosniff No Your own code, the container or the proxy
X-Frame-Options No Your own code, or the frame-ancestors directive of the CSP
Referrer-Policy No Your own code, the container or the proxy
Permissions-Policy No Your own code, the container or the proxy

X-XSS-Protection controlled a filter that current browsers no longer have. Leave it out; the Content Security Policy replaces it.

Stop other sites from framing your pages

The CSP directive frame-ancestors is the current replacement for X-Frame-Options:

getCspSettings().blocking().add(CSPDirective.FRAME_ANCESTORS, CSPDirectiveSrcValue.SELF);

Add headers to every page

Override setHeaders in your base page. Call super.setHeaders to keep the caching headers.

BasePage.java

@Override
protected void setHeaders(WebResponse response) {
    super.setHeaders(response);
    response.setHeader("X-Content-Type-Options", "nosniff");
    response.setHeader("Referrer-Policy", "strict-origin-when-cross-origin");
}

Add headers to every response

A request cycle listener also reaches resources, Ajax responses and redirects. Set the headers both when the handler is resolved and after it has run, the way Wicket’s own COOP and COEP listeners do, so they survive a redirect to a buffered response:

SecurityHeadersListener.java

public class SecurityHeadersListener implements IRequestCycleListener {
    @Override
    public void onRequestHandlerResolved(RequestCycle cycle, IRequestHandler handler) {
        setHeaders(cycle);
    }

    @Override
    public void onRequestHandlerExecuted(RequestCycle cycle, IRequestHandler handler) {
        setHeaders(cycle);
    }

    private void setHeaders(RequestCycle cycle) {
        if (cycle.getResponse() instanceof WebResponse response && response.isHeaderSupported()) {
            response.setHeader("Strict-Transport-Security", "max-age=31536000; includeSubDomains");
            response.setHeader("X-Content-Type-Options", "nosniff");
        }
    }
}

WicketApplication.java

getRequestCycleListeners().add(new SecurityHeadersListener());

Do not set Content-Security-Policy or the cross-origin policies this way: Wicket already sends them, and a second value either replaces Wicket’s policy or is combined with it by the browser.

Require HTTPS in web.xml

The servlet container can redirect every plain HTTP request to HTTPS:

web.xml

<security-constraint>
    <web-resource-collection>
        <web-resource-name>Entire application</web-resource-name>
        <url-pattern>/*</url-pattern>
    </web-resource-collection>
    <user-data-constraint>
        <transport-guarantee>CONFIDENTIAL</transport-guarantee>
    </user-data-constraint>
</security-constraint>

Require HTTPS covers HTTPS in Wicket itself.

After adding headers, check that the application still works: Strict-Transport-Security with includeSubDomains affects every subdomain for as long as max-age says, and a strict frame-ancestors breaks pages that are meant to be embedded.

How-to guides

  • Log users in Add a sign-in page with wicket-auth-roles, send anonymous users there when a page needs a signed-in user, and sign them out again.
  • Restrict access by role Allow pages, components, actions and resources only for users with a given role, with annotations on classes and packages or in code.
  • Require HTTPS Serve pages over HTTPS with HttpsMapper and @RequireHttps, and set up the container so redirects and absolute URLs use the right host.
  • Protect against cross-site request forgery Refuse link clicks, form submits and Ajax calls that another site makes on behalf of your users, with ResourceIsolationRequestCycleListener.
  • Configure the Content Security Policy Work with the strict Content Security Policy Wicket sends by default, allow extra sources, report violations, and move inline scripts and styles out of the markup.
  • Isolate the page with COOP and COEP Set the Cross-Origin-Opener-Policy and Cross-Origin-Embedder-Policy headers, which Wicket sends by default, to isolate your pages from other origins.
  • Control which package resources are served Allow or block files on the classpath that browsers may request as package resources, with patterns on SecurePackageResourceGuard.
